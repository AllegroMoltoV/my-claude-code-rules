# 長期タスクの状態管理 (Beads)

長期タスクの状態、依存関係、ブロッカー、次の作業は Beads (`bd`) で永続管理します。コマンドの網羅的な一覧と使い方は、セッション開始時とコンテキスト圧縮後にフックが注入する `bd prime` の出力を参照してください。本ルールは `bd prime` が扱わない判断基準を定め、判断と不可分なコマンドやフラグは判断基準とあわせて記載します。

## 状態の正本

タスク状態の正本は Beads のデータベースだけです。

- 会話履歴、コンテキスト圧縮の要約、`handoff.md`、`docs/` 配下のメモを状態の正本にしてはいけません。これらはコンテキスト圧縮で失われるか、更新が追いつかず実態とずれます。
- セッション内の TodoWrite や TaskCreate は、そのセッション限りの手順チェックリストです。セッションをまたぐ状態は必ず `bd` に書いてください。
- 既存の `handoff.md` を見つけたときは、内容を後述の「決定と知見の置き場所」にしたがって振り分けてください。残っている作業は `bd create` へ、そのリポジトリで今後も効く知見や決定は `bd remember` へ移し、`handoff.md` には Beads を参照する旨だけを残します。

## 使う場面と使わない場面

git リポジトリでは Beads を既定として使います。ただし全ての作業を登録するわけではありません。

登録するのは次の場合です。

- 1 セッションで終わらない見込みの作業
- 依存関係やブロッカーがあり、着手順を管理する必要がある作業
- 作業中に見つかった、後で対応すべき課題

登録しないのは次の場合です。

- 数分から数十分で完結し、そのセッション内で確実に終わる単発作業
- 質問への回答、調査結果の報告だけで完結するやり取り

判断に迷う場合は登録してください。不要だった記録の削除は容易ですが、失われた文脈は復元できません。

## セッション開始時の手順

フックが `bd prime` の workflow context と永続メモリを、続けて in_progress、ready、blocked の一覧を自動で注入します。

1. 注入された一覧を読み、前回どこまで進んでいたかを把握する
2. 一覧が空でも `.beads/` があるなら、新規タスクの登録要否を判断する
3. 何も注入されていないなら、そのリポジトリは Beads 未導入かオプトアウト済みである

## 未導入リポジトリでの初期化

git リポジトリで長期タスクを扱うのに `.beads/` が無い場合、リポジトリ直下に `.beads-optout` が無いことを確認したうえで、次のコマンドで初期化してください。

```bash
bd init --stealth --skip-agents --non-interactive --init-if-missing
```

- `--stealth`: beads のファイルを `.git/info/exclude` で除外し、共有リポジトリを汚さない。git コミットも作らない
- `--skip-agents`: `CLAUDE.md`、`AGENTS.md`、プロジェクト側フックの生成を抑止する。フックはグローバルに導入済みで、重複させないため
- `--non-interactive`: 対話プロンプトを出さない
- `--init-if-missing`: 初期化済みなら何もせず正常終了する

フラグを省いた素の `bd init` は、`CLAUDE.md` と `AGENTS.md` とプロジェクト側フックを作成したうえで git コミットまで自動作成します。これらは意図しない変更になるため、上記のフラグを必ず付けてください。

## オプトアウト

リポジトリ直下に `.beads-optout` を置いたプロジェクトでは、Beads を初期化しても提案してもいけません。

```bash
touch .beads-optout
```

`.beads/` が無いプロジェクトではフックは何も出力しないため、未初期化のリポジトリはそれだけで Beads が動作しない状態です。初期化済みのリポジトリを離脱させるときは、必要なら `bd export` で退避したうえで `.beads/` を削除してください。

## 記録するタイミング

**作業の終わりにまとめて書こうとしてはいけません。** セッションはコンテキスト圧縮や利用者の離席で予告なく途切れ、終わりに書く運用は途切れた時点の作業内容をそのまま失います。

記録は、事実が確定したその場で書いてください。こまめに commit するのと同じ発想で、次のいずれかが起きたらその時点で書きます。置き場所は事象ごとに違います。

| 起きたこと | 置き場所 |
| --- | --- |
| 方針を決めた | 課題に `bd note`。以後も効き続ける方針なら `bd remember` にも書く |
| 検証が通った、または失敗した | 課題に `bd note` |
| ブロッカーが判明した | 課題に `bd note` を書き、`bd dep add` で依存関係を登録する |
| ブロッカーが解消した | 課題に `bd note` |
| 後で対応すべき課題を見つけた | `bd create` で新しい課題として登録する。現在の課題への `bd note` で代替してはいけない |
| 利用者から判断を受け取った | 後述の「決定と知見の置き場所」にしたがって振り分ける |

`bd update --claim` は着手時に、`bd close` は完了時に実行します。1 つの作業が長引くときは途中経過を `bd note` に足していき、こうしておけば、いつ途切れても失われるのは直前の数分だけになります。

## 記録の書き方

コマンドやテストで確認した内容は確認方法とともに `bd note` に書き、未確認の想定は未確認と明記してください。

タスクを完了するときは、実施内容と検証結果 (未検証ならその旨) を `--reason` に残してください。何をしたかだけでなく、正しさをどう確かめたかまで書きます。

```bash
bd close <id> --reason="実施: <変更内容>。検証: <実行したコマンドと結果>"
```

## 決定と知見の置き場所

**利用者から受け取った判断を、次のセッションに引き継がれない場所へ書いてはいけません。** 同じ判断を何度もさせることになり、一度決着した事項を再度確認するのは利用者の時間を奪う行為です。

次のセッションに注入されるものと、されないものを取り違えないでください。

| 置き場所 | 次のセッションに注入されるか |
|---|---|
| `bd remember` の永続メモリ | **される** |
| open や in_progress や blocked の課題 | **される** |
| Claude Code の auto memory | **される** |
| `rules/` 配下のルールファイル | **される** |
| `bd close --reason` の完了理由 | **されない** |
| `bd note` の追記 (課題が closed の場合) | **されない** |

`--reason` と `note` は、その課題を `bd show` で開いたときにしか読まれません。作業の経緯を残す場所としては正しいですが、課題を close した瞬間に見えなくなるため、**今後も効き続ける決定をここに書いてはいけません。**

置き場所は、記録する内容が何についてのものかで決めます。

| 内容 | 置き場所 | 例 |
| --- | --- | --- |
| その課題に固有の経緯と検証結果 | `bd note`、完了時は `bd close --reason` | この課題では A を試して失敗した |
| そのリポジトリの作業で繰り返し必要になる技術的知見、確定した設計判断、再現手順、対象外とする範囲 | `bd remember` | この方式で進める、このディレクトリは扱わない、この手順で再現する |
| 利用者の好み、作業の進め方への指示、環境の事実 | Claude Code の auto memory | 報告は結論から書く、この PC ではシンボリックリンクを作れない |
| 全プロジェクトで守る規約 | `rules/` 配下のルールファイル | コミットメッセージは日本語で書く |

判定に迷ったときは、**その記録が次に必要になる場面**で決めてください。同じリポジトリの作業を再開したときだけ必要なら `bd remember`、別のプロジェクトでも必要なら auto memory かルールファイルです。

Claude Code の auto memory は `~/.claude/projects/<project>/memory/` に置かれ、プロジェクトごとに分かれています。すべてのプロジェクトで守らせたい規約を auto memory に書いても他のプロジェクトには届かないため、その場合はルールファイルに書いてください。

同じ内容を複数の場所に重複して書かないでください。更新が片方だけに入り、内容がずれます。

`bd prime` の出力には `MEMORY.md` を使うなという記述がありますが、Claude Code の auto memory は Beads とは別の用途で併用します。タスク状態と技術知見を Beads に、利用者の好みと作業方針を auto memory に置き、両者を混在させないでください。

## 同期

`bd dolt push` はリモートへの送信です。利用者が明示的に指示したときだけ実行してください。ローカルの `.beads/` に書き込むだけで、セッションをまたぐ引き継ぎは成立します。
