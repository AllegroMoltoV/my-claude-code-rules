# ソフトウェアテスト

## 書く範囲

正常系のテストを際限なく足さない。将来の変更で壊されると守りたいラインを決め、そこにだけ最小限書く。ほかのファイルの関数への依存、読み込み順や登録順への依存、依存ライブラリの更新のように、無関係に見える機能同士が関係する経路を重点的に守る。壊れても問題ない部分には書かない。

バグの帰結が情報漏洩や権限の逸脱のような危険側なら、その異常を検知するテストを書く。表示が減る、処理が呼ばれない、といった安全側で実装の写しになる次のテストは書かない。

- 定数配列や、`arr.map(fn)` のようにロジックの無い薄いラッパーの単体テスト
- フィクスチャを整形関数に渡し、出力の部分文字列を確かめるテスト
- スキーマのバリデーターを直したときに、その書き方だけを確かめるテスト
- 処理の呼び出しを消した修正で、消した処理が実行されないことを確かめるテスト
- バグ修正で念のために足す回帰防止の正常系テスト。確認は手元での実行で済ませる
- 重要度の低い機能で、レスポンスにフィールドが存在することを確かめるテスト

## アクセス権限

権限が無い人のアクセスが拒否されることをテストする。権限がある人に 200 が返るテストだけでは何も守れない。権限が無い人がアクセスできる不具合は、多くが報告されないまま重大な実害に至る。テストを削るときも、この拒否のテストは残す。

- 守りたい境界の際を、危険側から試す。メンバーだけが読めるページなら、ログインしているがメンバーではない人で 403 を確かめる。ログインしていない人で試すと、ログインの有無という別の境界のテストになる。
- 期待するステータスコードは厳密に確かめ、403 を期待する箇所で 404 が返ったら落とす。
- 全組み合わせを網羅せず、境界の最小の組だけを書く。誰でも読める公開リソースなら、最も権限が低い人の 1 件で足りる。
- 一覧や検索のように、含まれるものによって権限が決まる API では、含まれてはいけないものが含まれないことを確かめる。
- 権限を厳しくする変更では、制限したい相手が拒否されることをテストする。権限を緩める変更では、変更前のコードでも通るテストを、指示なしに足さない。足すべきと判断したときは、足す前に依頼者に確認する。
- アクセス権限のテストはコントローラーへのリクエストで、パス・利用者の種別・期待するステータスコードの表として書く。データ形式のテストとは分け、データ形式はメソッドの返り値で確かめる。

## フィクスチャの仮名

仮のメールアドレスやユーザー名のローカル部には、依頼者自身のハンドルを使う。`taro` のような汎用の名前は、実在の人物のアカウントと一致しうる。ドメインには `.example` を使う。既存のテストが別のドメインを使っていれば、それに合わせる。

## テストランナーの移行

移行の前後で、実行されるテストの合計件数が変わらないことを確かめる。
