# 技術ブログ執筆

技術ブログの執筆戦略、初稿、改稿、校正に適用する。日本語の記法は `~/.claude/rules/documentation.md` にしたがい、本スキルには収録しない。この規約は Markdown ファイルを扱うときにだけ自動で読み込まれるため、記事を Markdown 以外で書く場合や、読み込まれていない場合は、書き始める前に Read で読む。

## 執筆戦略

読者の悩みとその理由を起点に、記事が提供する価値を定める。技術の紹介を起点にしない。対象読者、中心となる主張、主張を支える証拠、記事構成、考察の方向、記事と公開情報の範囲、完了条件を執筆戦略に記す。戦略には現在有効な方針だけを残し、題名の決定過程、採用しなかった案、修正履歴、記事本文を混ぜない。

既存記事から媒体の形式と執筆者の文体を調べ、見出し構成、分量、コード表示、補足記法を合わせる。レベル 2 見出しには「構成」「検証と結果」「考察」「まとめ」など、読者に内容が伝わる一般的な名称を使う。公開価値の高い知見に絞り、記事の理解に不要な内部事情を省く。

## 主張と証拠

実験方法と検証したい仮説を対応させる。正解情報の混入、不公平な比較、実務と異なる前提を調べる。

```
悪い例: 回答を得る能力の評価で、入力に正しい回答を含める。
```

証拠が足りないときは、追加検証か主張範囲の縮小を選ぶ。記事の完成を優先して結論を先に作らない。読者が閲覧できないローカル文書への参照だけで済ませず、記事内に結果や出力の抜粋を示す。公開記事からローカルパス、非公開のプロジェクト名、個人情報を除く。

## 題名と概要

題名には検索される技術名と最も価値の高い結果を含め、結果を列挙しない。`excerpt` は 2 文にし、1 文目で試み、2 文目で結論を示す。題名の言い換えを繰り返さず、別の情報を補う。題名と `excerpt` は本文より抽象度を上げ、説明前の内部用語、候補数、評価区分を持ち込まない。題名を変えた後は URL スラッグとの整合を直す。

## 本文と考察

コード例は読者に必要な範囲を載せる。Zenn のコードブロックにファイル名を示す場合は `python:sample.py` の形式を使う。全体の理解が必要なコードは `:::details` に折り畳んで全文を載せる。

考察では、証拠から考えられる実務での利用場面、期待できる利点、導入条件などを述べる。推測は、でしょう、と思います、などで明示し、断定しない。考察を免責事項の列挙にしない。

## 改稿と校正

利用者の修正指示からは、表面の言い換えではなく修正の理由を読み取る。同じ問題を題名、`excerpt`、本文、表、執筆戦略でも直し、今後の記事にも通じる学びは auto memory に残す。利用者の提案を採用する前に、証拠、計算、日本語、記事全体との整合を確認する。校正時は、公開範囲、証拠の見せ方、主張と結果の一致も読み直す。
