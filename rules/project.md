# プロジェクト管理の規約

本プロジェクトの管理においては下記を遵守してください。事実の検証、調査の先行、報告文の書き方、外部操作や破壊的操作の扱いなど、作業の進め方に関する行動原則は `working-principles.md` にまとめています。

- バグが出たときは場当たり的な対応をせず、まず調査し原因をつきとめたうえで、手戻りを最小限におさえた改善対応を行ってください。
- ブランチ名に master を使わず main を使うようにしてください。
- コミットメッセージは日本語で書いてください。
- 新たな計画を作成した際は、都度 `.prompts/PLANS/` 配下に新規で保存してください。
  - プランファイルは、ゼロ文脈で読んでそのまま作業開始できる自己完結した内容にしてください。検証を別のエージェントに任せるため、対象ファイルパス、URL、コマンド例など作業に必要な具体的情報を漏らさず、かつ重複した記述は排除します。
  - 計画を保存したら、独立した文脈のサブエージェントに反証させてください。渡すのは計画ファイルのパスと対象リポジトリの位置だけとし、会話の経緯や検討して捨てた案を渡してはいけません。
    - 親の文脈を継承する形式のサブエージェントは使ってはいけません。同じ前提を引き継いだ相手は結論を追認します。
    - 反証を行うサブエージェントには、このセッションで動いているモデルより低位のモデルを使用しないでください。
    - 指示は、レビューせよではなく、この計画が失敗する経路を挙げよ、の形にしてください。最初に問わせるのは、その作業は目的の達成に必要か、未確認の前提の上に立っていないか、より単純な方法はないか、の 3 つです。
    - 疑うのは計画が足した手段であって、依頼された目的そのものではありません。目的まで疑い返すと承認フローが重くなります。
    - 指摘には根拠 (確認したファイルと行、実行したコマンドと結果) を書かせてください。反証を求める指示は根拠のない懸念を作る圧力にもなるため、示せないものは未確認として分けさせます。
    - サブエージェントの出力をそのまま写さず、回答が計画を変えない指摘は落としてください。
  - 残った懸念点は `.prompts/DISCUSSIONS/` 配下に md ファイルとして書き、私に回答を求めてください。懸念点ごとに、推奨案を含む複数案を提示し、推奨案にはその旨を明記します。
  - 私の回答を得てから承認フローに進み、私が承認してから計画を実行してください。
  - CLI 操作で完結できるタスクは Claude Code 側で自律的に完結するプランを提示してください。人間の介入は意思決定、承認、外部認証など Claude Code では代替できない操作に限定してください。
  - 多段階の計画は、結果次第で以降の前提が変わる初手ステップ (情報取得や可否判定など) に絞って提示してください。続きはその結果を確認してから別の計画として立て、早い段階で前提を確証して無駄な計画立案や実装を避けます。
- .git/info/exclude に書かれた CLAUDE.md, .claude, .prompts などの除外設定は意図的なものです。作業時はこれを尊重してください。
  - .gitignore の内容が常に正しいか検討するようにしてください。.git/info/exclude に含まれているものを二重に除外する必要はありません。
- 複数コマンドが必要な場合は個別の Bash 呼び出しに分けてください。理由は承認ダイアログの削減ではなく、実行結果の可読性と `permissions.allow` への登録しやすさのためです。
  - `&&` や `|` でコマンドを連結しない。
    - 悪い例: `cd /d/work/editor-with-git/app && npx vitest run`
    - 良い例: `cd /d/work/editor-with-git/app` → `npx vitest run`
  - 承認要求が多いと感じたら、自己流の対策を考える前に `/fewer-permission-prompts` を実行してください。
  - ファイル編集の「以降すべて許可」はセッション限り、Bash コマンドの「以降すべて許可」はリポジトリとコマンドの組み合わせで恒久保存という違いがあります。`.git`、`.claude`、`.npmrc` などの保護パスは `bypassPermissions` モード以外では常に確認が入ります。
  - `--dangerously-skip-permissions` (bypassPermissions) は保護パスの確認ごと外れるため、隔離環境以外では使わないでください。
- git -C コマンドを使わず、cd で対応してください。
- .prompts/INSPECTIONS 配下の .sarif.json の分析のために、まず .prompts/INSPECTIONS/extract.py を作成し、必要な部分だけを抽出するようにしてください。
- 調査内容とレポートは `docs/reports` に、後から参照する価値があると判断した実行結果は `docs/logs` に蓄積してください。コンテキスト圧縮で情報が失われても、ファイルから再取得できる状態を維持するためです。
  - スクリプトの生の標準出力と標準エラーは、長時間の実行、再実行が困難な操作、後から診断が必要になりそうな実行に限り `.logs` に書きます。`.logs` は git の追跡対象外で共有もされないため、残す価値があると判断したものだけを `docs/logs` へ移し、同じログを両方に置いてはいけません。
  - `docs/INDEX.md` を作成・更新し、何がどこに書かれているかを一覧化してください。
- README にはプロジェクトの目的、背景情報、内容物、使い方を記載してください。末尾にはバージョンごとの更新情報を記載してください。
- 大量のファイル読み込みや、ログ・原因の丁寧な分析を伴う作業は、サブエージェントに委譲してください。独立した調査は並列に走らせ、コンテキストを浪費せず効率的に進めてください。
