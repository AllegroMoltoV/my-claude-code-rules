本プロジェクトに管理においては下記を遵守してください。
- 憶測で作業を行わず確かな根拠に基づいて作業を実施してください。たとえば、バグが出たときに場当たり的な対応をせず、まずは調査し原因をつきとめたうえで、手戻りを最小限におさえた改善対応を行ってください。
- ブランチ名に master を使わず main を使うようにしてください。
- コミットメッセージは日本語で書いてください。
- 新たな計画を作成した際は、都度 `.prompts/PLANS/` 配下に新規で保存してください。
  - 計画を立てた後は、その計画をノンバイアスで読み直し、懸念点を `.prompts/DISCUSSIONS/` 配下に md ファイルとして洗い出して、私に回答を求めてください。私の回答を得てから承認フローに進んでください。
    - 懸念点ごとに、推奨案を含む複数案を提示してください。推奨案にはその旨を明記してください。
  - 計画を立てた後は私に承認を促してください。私が承認してから計画を実行するようにしてください。
  - プランファイルは、ゼロ文脈で読んでそのまま作業開始できる自己完結した内容にしてください。
    - 対象ファイルパス、URL、コマンド例など、作業に必要な具体的情報を記載すること
    - 重複した記述は排除し、必要十分な情報量に留めること
  - CLI 操作で完結できるタスクは Claude Code 側で自律的に完結するプランを提示してください。人間の介入は意思決定、承認、外部認証など Claude Code では代替できない操作に限定してください。
  - 多段階の計画は、結果次第で以降の前提が変わる初手ステップ (情報取得や可否判定など) に絞って提示してください。続きはその結果を確認してから別の計画として立ててください。早い段階で前提を確証し、無駄な計画立案や実装を避けるためです。
- .git/info/exclude に書かれた CLAUDE.md, .claude, .prompts などの除外設定は意図的なものです。作業時はこれを尊重してください。
  - .gitignore の内容が常に正しいか検討するようにしてください。 .git/info/exclude に含まれているものを二重に除外する必要はありません。
- 複数コマンドが必要な場合は個別の Bash 呼び出しに分けてください。理由は承認ダイアログの削減ではありません。公式ドキュメント (code.claude.com/docs/en/permissions) によれば、複合コマンドは Claude Code がサブコマンドごとに許可判定し、一度承認した組み合わせは前後に何が付いても再利用されるため、分割しても判定条件自体は変わりません。実際の理由は、実行結果の可読性と、コマンドごとに `permissions.allow` へ登録しやすくするためです。
  - `&&` や `|` でコマンドを連結しない。
    - 悪い例: `cd /d/work/editor-with-git/app && npx vitest run`
    - 良い例: `cd /d/work/editor-with-git/app` → `npx vitest run`
  - パイプの代わりに一時ファイル (`.tmp` 配下) へリダイレクトし、結果は Read ツールで読む。テストの合否判定など判定に使う経路では、標準エラーも一時ファイルに記録し (`2>&1`)、握りつぶさないでください (`working-principles.md` の「エラーと証拠なしを同じ 0 件にしない」参照)。
    - 悪い例: `npx vitest run --coverage 2>/dev/null | tail -60`
    - 良い例: `npx vitest run --coverage > .tmp/cov.txt 2>&1` → Read ツールで `.tmp/cov.txt` を読む
  - 承認要求が多いと感じたら、自己流の対策を考える前に `/fewer-permission-prompts` を実行してください。トランスクリプトから頻出コマンドを拾い、`permissions.allow` の許可リストを自動生成します。
  - ファイル編集の「以降すべて許可」はセッション限り、Bash コマンドの「以降すべて許可」はリポジトリとコマンドの組み合わせで恒久保存です。次のセッションで編集だけ再度尋ねられるのは仕様です。
  - `.git`、`.claude`、`.npmrc` などの保護パスへの書き込みは、許可リストを整備しても `bypassPermissions` モード以外では常に確認が入ります。
  - 2026-08-14 以降、Pro/Max/Team の新規セッションでは auto モードが既定です。それでも本番デプロイや force push、IAM 変更、シークレットアクセス、大量削除は既定でブロックまたは確認対象です。`--dangerously-skip-permissions` (bypassPermissions) は保護パスの確認ごと外れるため、隔離環境以外では使わないでください。
- git -C コマンドを使わず、cd で対応してください。
- .prompts/INSPECTIONS 配下の .sarif.json の分析のために、まず .prompts/INSPECTIONS/extract.py を作成し、必要な部分だけを抽出するようにしてください。
- 調査内容とレポートは `docs/reports` に、後から参照する価値があると判断した実行結果は `docs/logs` に蓄積してください。コンテキスト圧縮で情報が失われても、ファイルから再取得できる状態を維持するためです。
  - スクリプトの生の標準出力と標準エラーは、長時間の実行、再実行が困難な操作、後から診断が必要になりそうな実行に限り `.logs` に書きます。短時間で完結する単純なコマンドまで機械的にログ化する必要はありません。`.logs` は git の追跡対象外で、共有もされません。残す価値があると判断したものだけを `docs/logs` へ移してください。同じログを両方に置いてはいけません。
  - `docs/INDEX.md` を作成・更新し、何がどこに書かれているかを一覧化してください。
- README にはプロジェクトの目的、背景情報、内容物、使い方などを網羅的に記載し、初見の人が全貌を把握し滞りなくタスクを進められるようにしてください。 README の末尾にはバージョンごとの更新情報を記載してください。
- 大量のファイル読み込みや、ログ・原因の丁寧な分析を伴う作業は、サブエージェントに委譲してください。独立した調査は並列に走らせ、コンテキストを浪費せず効率的に進めてください。
- 事実の検証、調査の先行、報告文の書き方、外部操作や破壊的操作の扱いなど、作業の進め方に関する行動原則は `working-principles.md` にまとめています。併せて遵守してください。
