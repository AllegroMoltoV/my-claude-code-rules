# ソフトウェアテスト

AI は放っておくと正常系のテストを際限なく書き、アクセス権限の境界のテストを書くのが下手である。本スキルの基準は、際限の無い正常系のテストをやめ、情報漏洩を避けるために重大な境界条件を見つけてテストするためのものである。テストを書くとき、テストを足す要否を決めるとき、落ちたテストを直すとき、テストランナーを移行するとき、テストをレビューするときに従う。

## 書く範囲

守りたいラインを決めて、そこにだけ最小限のテストを書く。テストは、その PR が正しいことの証明であると同時に、別の変更によって壊されないよう守るものである。将来壊れそうな場所を予測し、そこにテストを置く。ラインを決めずに書くと、仕様変更のたびにテストの大半を書き直すことになる。その作業でミスが入って情報が漏洩するため、テストは実質的に何も守らない。

- 別の機能追加によって壊されうると考えた箇所に、重点的にテストを仕込む。別ファイルの関数を 1 つだけ `import` して使っている、ファイルの読み込み順や関数の登録順に依存している、依存ライブラリを更新した、ライブラリ同士の相性が悪い、といった経路で、無関係だと思っていた機能同士がどこかで関係している。
- 壊れても問題ない部分にはテストを書かない。

## 情報漏洩の検査

情報が漏洩していないことを重点的にテストする。メンバーであればアクセスできることではなく、メンバーではない人のアクセスが拒否されることをテストする。テストの書きすぎを防ぐために対象を削るときも、アクセスを正しく拒否できること、つまり情報漏洩を防ぐテストは書く。

権限がある人がアクセスできない不具合は、その人が見られないと報告してくれる。権限が無い人がアクセスできてしまう不具合は、その多くが報告されない。本人は自分に権限があって正常に見えているだけだと思っていることがあり、報告が面倒なこともあり、他人の非公開情報が見えても本人に実害が無いことも多い。重大な実害が発生してから報告が届き、謝罪のプレスリリースを出すことになる。

- 権限を厳しくする変更では、制限したい相手が実際に拒否されることをテストする。
- 権限を緩める変更では、変更前のコードでも通り、バグ修正でもないテストを、指示されない限り足さない。それでも足すべきと判断したときは、足す前に依頼者の判断を仰ぐ。緩めた結果として残すべき制限が外れていないことは、レビューで確かめる。
- 必要なラインの際を見極め、その危険側を集中的にテストする。アクセス権限の境界は 1 つではない。
  - プロジェクトのメンバーだけが読めるページなら、守りたいのはメンバーである人とない人の境界である。ログインしているがメンバーではない人にアクセスさせ、403 が返ることをテストする。
  - ログインしていない人で試すのは誤りである。ログインの有無という別の境界をテストしたことになる。
- 期待するステータスコードは厳密に確かめる。403 を期待する箇所で 404 が返ったら、落ちるようにテストを書く。
- 権限がある人に 200 が返ることのテストだけでは、ほとんど何も守れない。権限が無い人にも 200 が返っている可能性が残るためである。今後もメンテナンスを続ける余裕と、テストの実行時間の余裕があるなら書いてよい。
- 全組み合わせを網羅せず、権限の境界の最小の組だけを書く。誰でも読める公開プロジェクトの読み取りなら、最も権限が低い人が通る 1 件で足りる。
- 実装の側では逆に、権限があることを確認する。権限の種類は将来必ず増える。権限があることを確認する実装なら、増えた権限の人にはデータが返らないため、安全側に倒れる。

## データ形式とアクセス権限の分離

データ形式のテストとアクセス権限のテストは分けて書く。

- アクセス権限のテストは、コントローラーにリクエストし、拒否を示すステータスコードで確かめる。パス、ユーザーの種別、期待するステータスコードの組み合わせを表として書くと、まとめて確かめられる。メンテナンスが大変でなければ、境界の際以外を充実させてよい。
- 一覧や検索のように、含まれるものによって権限が決まる API では、含まれてはいけないものが含まれないことを確かめる。
- データ形式のテストは、メソッドの返り値を確かめる。単純な API ならまとめてテストしてよい。
- 重要度の低い機能で、レスポンスにフィールドが存在することを確認する類のテストは書かない。書き始めると際限が無い。使っていれば気づく程度の不整合は、見つけ次第直せばよい。

## 書かないテスト

実装の写しになるテストを書かない。正常系のテストを際限なく足すと、実装の単なるコピーになる。実装を変えるときに二重に書き換えることになり、変更のコストを上げるだけで何も守らない。

テストを足す前に、実装の量との釣り合いと、バグがあったときに起きる事象を考える。バグの帰結が情報漏洩や権限の逸脱のような危険側なら、その異常を検知するテストを検討する。表示が減る、処理が呼ばれない、といった実害の無い安全側なら書かない。次のテストは、安全側で実装の写しになるものなら書かない。

- 定数配列や、`arr.map(fn)` のようにロジックの無い薄いラッパーの単体テスト
- フィクスチャを整形関数に渡し、出力の部分文字列を確かめるテスト
- スキーマのバリデーターを直したときに、バリデーターが正しく書けていることを確かめるだけのテスト
- 処理の呼び出しを消しただけの修正で、消した処理が実行されないことを確かめるテスト
- バグ修正で、直したことを確かめるための念のための回帰防止の正常系テスト。将来誰かが再導入したら検出できる、という動機は弱く、確認は手元での実行で済ませる

## フィクスチャの仮名

テストのフィクスチャや設定の例に仮のメールアドレスやユーザー名を書くときは、ローカル部に依頼者自身のハンドルを使う。taro のような汎用的な人名は、実在の人物のアカウントと一致すると問題になる。依頼者自身のハンドルなら、実在しても本人である。ドメインには `.example` を使う。既存のテストが別のドメインを使っていれば、それに合わせる。

## 落ちたテストの直し方

テストが落ちたときに、テストを通すことだけを目的として実装を直したり、テストの根本的な方針や機構に手を加えたりしない。

## テストランナーの移行

テストランナーを移行するときは、移行の前後で実行されるテストの合計件数が変わらないことを確かめる。
