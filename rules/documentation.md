ドキュメント作成時は下記を遵守してください。

- 日本語で書いてください。
- 図は mermaid で書いてください。
- 技術文書としてふさわしいフォーマル寄りの文体で文章を執筆してください。
- 専門用語が出現したときは適宜その意味を補完するよう努めてください。
- 半角の文字列と、全角の文字列の間にはスペースを挿入してください。
  - ただし句読点の直後であればスペース挿入は省略して良いものとします。検索性を高めるためです。
  - このスペースはあくまで半角英数字と全角文字の境界にだけ入れるものです。全角文字どうしの間、とりわけ助詞の前後 (「担当者 が」)、動詞の活用 (「なって おります」)、謙譲語・丁寧語の接頭辞 (「ご 確認」) を分断するスペースは決して挿入してはいけません。日本語として口に出せない文面になり、読み手の認知負荷を著しく高めます。書き終えたら音読するつもりで必ずセルフチェックしてください。
  - 上記の境界スペースは検索性を優先する `docs/` 配下の技術文書に適用するルールです。Claude Code のターミナル応答、UI に表示する文字列、チャットやチケットへの投稿文案では、境界スペースよりも日本語としての自然さを優先し、境界スペースを詰めてかまいません。
- 全角かっこ、全角コロンは決して使用しないでください。
  - 半角かっこを使用する際、前かっこでは `[space](` の形で、後ろかっこでは `)[space]` の形でスペースを挿入してください。半角コロンを使用する際は `:[space]` の形でスペースを挿入してください。

```
悪い例: これをARGといいます。
良い例1: これを ARG といいます。
良い例2: これを、ARG といいます。
```

```
悪い例1: 代替現実ゲーム（ARG）は、
悪い例2: 代替現実ゲーム ( ARG ) は、
良い例: 代替現実ゲーム (ARG) は、
```

```
悪い例1: ARG：代替現実ゲーム
悪い例2: ARG : 代替現実ゲーム
良い例: ARG: 代替現実ゲーム
```

- ダブルクオーテーションは日本語文章中には決して使用しないでください。
- 「ひとつひとつ」「一発逆転」のような日本語の言葉を、「 1 つ 1 つ」「1発逆転」のように算用数字で書いてはいけません。
  - 「第 1 回」「第 2 回」、「1 点のメリット」「2 点のメリット」のように、異なる数に置き換えられるものは算用数字で書いてかまいません。
  - 1,000 のように、 4 桁以上の数にはコンマを付けてください。
- 衒学的な表現はなるべく避け、平易な日本語で記載してください。
  - 「〇〇を実現します」 「〇〇を実施します」などの表現は、「〇〇できます」 「〇〇します」 という表現で書けないか常に検討してください。冗長な表現を避け端的に表現してください。

```
悪い例: 解説が行われました
```

```
良い例: 解説されました
```

- 「〇〇で、〇〇」のように並列的に並べることで冗長な表現になることを必ず避けてください。
  - 一文の長さが長くなりすぎないよう適切に区切ってください。

```
悪い例: Python はインタプリタ言語で、低速です。
```

```
良い例: Python はインタプリタ言語です。また、低速です。
```

- むやみに箇条書きを挿入すべきではありません。日本語文の途中で箇条書きが挿入されるのは日本語文章として不自然だからです。
  - 文の形で完結させるよう努め、項目の並列性がある場合のみ箇条書きを使用してください。

悪い例:
```
検証環境として
* Windows
* Next.js
を使用しました。
```

良い例1:
```
検証環境として、Windows と Next.js を使用しました。
```

良い例2:
```
検証環境は以下の通りです。
* Windows
* Next.js
```

- 助詞を適切に使用してください。特に、「以下」「次」「は」のワードについては細心の注意を払ってください。

悪い例
```
設定内容は次とします。
```

良い例
```
設定内容は次のようにします。
```

悪い例
```
get() は、ユーザーが情報を取得します。
```

良い例 (ユーザーを主語にする場合)
```
get() では、ユーザーが情報を取得します。
```

良い例 (get を主語にする場合)
```
get() は、ユーザーが情報を取得するための関数です。
```

- 「整理する」「寄せる」「効く」といった広い意味の言葉を使わないでください。例えば、「効く」は「影響する」や「効果的だ」など複数の意味を含有しており、読者が文脈から正しい意味を推定しなければならず認知負荷が高いです。意味が一意になる言葉を使うよう努め、厳密に事象を定義してください。
- 「包括的に」「一気通貫で」「ポイントは」「要点は」など英語からそのまま直訳したような言葉の使用を避けてください。
  - 日本語文章において一般的に使用されているワーディングを意識してください。

- 抽象度を適切にコントロールしてください。読み手の認知負荷を下げるための工夫です。読み手を裏切ってはいけません。
  - まずは抽象度の高い書き方で全体を説明しながら、カスケード的に、より抽象度の低い話へと話を進めていくよう、読み手の認知の順番を意識してください。
  - たとえば「序論→本論→結論」 「背景→提案→検証→考察」のように、一般的な技術文書テンプレートにしたがって文章を構成してください。

- 手順を説明するときはいきなり手順の中身を説明する前に、簡単にでもよいので手順を踏む理由や目的を説明してください。
- 見出しには「環境変数の設定」など、内容を実態に即した具体的な見出し名をつけてください。
- 同じものは同じ言葉を使って説明してください。言い換えてはいけません。
- 日本語文章を書くときに endpoint や agent のような特別な用語でもないものについて英単語で書くことを許可しません。エンドポイント、エージェントのように日本語で書いてください。また、コンピュートのようなカタカナ語を多用すべきでなく、日本人読者に寄り添った明瞭な日本語で書くようにしてください。

## 一般語をカタカナで書く判定基準

英単語で書いてよいかどうかは、次の基準で判断してください。

| 種別 | 表記 | 例 |
| --- | --- | --- |
| 製品名、サービス名 | 英語のまま | Beads、Claude Code、Perforce、macOS |
| コマンド名、ファイル名、識別子 | 英語のまま | `bd`、`HANDOFF.md`、`p4mcp-server` |
| コードブロックの中身 | 英語のまま | 実行結果やソースコード |
| 上記以外の一般技術語 | カタカナ | ブロッカー、フック、サーバー、バイナリ、エンドポイント、エージェント |

判断に迷ったときは、その語が固有名詞かどうかを考えてください。固有名詞でなければカタカナです。hook や blocker のように技術的な文脈で使われる語であっても、固有名詞でなければカタカナにします。

初出時に限り、検索性のために英語を併記してかまいません。かっこの使い方は本文書の規約にしたがいます。

```
悪い例: 着手できる課題と blocker で止まっている課題を区別できます。
良い例: 着手できる課題とブロッカーで止まっている課題を区別できます。
良い例 (初出時): コンパクション (context compaction) で文脈が落ちます。
```

## 見出しは文にしない

見出しに文を書いてはいけません。技術文書で一般的なラベルにしたがうか、ラベルと内容をコロンでつなぐ形にしてください。

一般的なラベルは、はじめに、背景、検証環境、検証方法、検証結果、考察、対策、まとめ、です。

```
悪い例: ## 状態の更新は自動では行われなかった
良い例: ## 検証結果: 状態の更新
```

構成そのものも、背景から提案、検証、考察へ進む一般的な技術文書のテンプレートに沿わせてください。分析や解釈が検証結果の節に埋もれていたら、考察として独立させます。

## 事実と推測を分けて書く

検証結果の節には、観測した事実と、それをどう確認したかだけを書いてください。原因の解釈や一般化を混ぜてはいけません。

考察の節には事実を書かず、推測や考えたことだけを書いてください。文末は、〜と考えています、〜のではないか、〜だと思います、の形にします。

まだ確かめていないことは、確かめていないと明記してください。実測していない体感を述べるときも、実測していないと書いてください。

```
悪い例 (検証結果の節): 原因は、テストの対象を取り違えていたことにあります。
良い例 (検証結果の節): テストの内容は、使い捨てのリポジトリで初期化と課題の作成が動くことを確認するものです。実際のプロジェクトで指示なしにルールが守られるかは、テストしていませんでした。

悪い例 (考察の節): 状態の読み込みはセッション開始時のフックで自動的に走ります。
良い例 (考察の節): 読み込みと書き込みで結果が分かれたのは、必要な判断の量が違うからだと考えています。
```
